# MRL External Material and Historical Extension Map v1

`origin_signature: MrLiouWord`

## 1. Binding definition

This specification is one indivisible operating chain. It defines who is upstream, who is downstream, where external material enters, where MRL ownership begins, how MRL-native products operate, and how evidence returns to the mother system. No layer may be extracted and treated as the whole system.

MRL keeps its own names, history, modules, products, and extensions complete. External platform names remain available to their original owners and users. MRL records those platforms as external material or provider sources, then builds MRL-owned interpretation, interface, runtime, memory, orchestration, product, and archive layers without erasing either side.

## 3. Upstream and downstream definitions

### Upstream authority

Upstream means the layer that defines identity, law, scope, ownership, naming, and acceptable transformation.

```text
Mr.liou / MrLiouWord
  -> MRL
  -> MRL_Mother
  -> MrliouAI
  -> MRL control and extension modules
  -> MRL-native products
```

No downstream module may redefine an upstream identity. `MrlAPI`, `mrlclaude`, `mrlcloud`, `FlowAgent`, adapters, runtimes, repositories, providers, and deployment platforms cannot replace or supersede MRL.

### External source direction

External providers are not authority upstream of MRL. They are upstream only as the original source of their own API, SDK, model, endpoint, service, or document.

```text
External provider source
  -> external material record
  -> MRL adapter boundary
  -> MRL interpretation and control
  -> MRL-owned extension
  -> MRL-native product or runtime
```

### Downstream execution direction

Downstream means implementation and execution under MRL definitions.

```text
MRL law and registry
  -> MrliouAI operating identity
  -> MrlAPI / mrlclaude / mrlcloud
  -> FlowAgent and other MRL-native modules
  -> runtime carrier
  -> task execution
  -> result and evidence
```

### Return direction

Every downstream execution must return evidence upstream.

```text
execution result
  -> trace and dependency record
  -> source/provenance association
  -> verification
  -> MRL_Mother memory and archive
  -> MRL historical lineage
```

## 5. Module responsibilities

### MRL

- Owns canonical system identity, laws, history and naming boundary.
- Determines what is internal, external, material, product, runtime, adapter or archive.
- Cannot be replaced by a provider, product, repository, runtime or deployment name.

### MRL_Mother

- Holds root law, schemas, registries, source records, memory, runtime traces and historical lineage.
- Receives all execution evidence and backfills it into the mother system.
- Is the authoritative integration point for historical reconstruction.

### MrliouAI

- Represents the unified MRL system identity in active operation.
- Coordinates MRL extensions and products.
- Does not delete or absorb the name `FlowAgent`; FlowAgent remains a distinct MRL-native product module.

### MrlAPI

- Accepts requests from MRL products and control surfaces.
- Applies MRL authentication, policy, routing, memory, trace and orchestration.
- Calls external APIs through provider adapters while preserving provider-required names at the boundary.
- Returns normalized results and evidence to MRL_Mother.

### mrlclaude

- Marks the MRL-owned integration and derived workflow built from Claude material or provider access.
- Keeps `Claude` as the external source name where provider identity is required.
- Adds MRL context, memory, policy, trace, orchestration and historical linkage.

### mrlcloud

- Controls MRL-owned deployment, synchronization, infrastructure mapping and portability.
- Keeps provider project IDs, endpoints and resource identifiers unchanged when technically required.
- Maps provider resources back to MRL-owned service, module, dependency and history records.

### FlowAgent

- Is an original MRL product module, not an external alias and not a deprecated compatibility name.
- Keeps its full product identity, source history, package lineage, runtime versions, interfaces and documentation.
- Consumes MRL services such as MrlAPI, mrlclaude and mrlcloud without becoming subordinate to an external provider.
- Returns task state, traces, memory and results to MRL_Mother.

### External providers and platforms

- Retain ownership of their original platforms, APIs, SDKs, models, endpoints and trademarks.
- Are classified inside MRL as external material, source, provider or execution dependency.
- Cannot become the MRL system identity or erase MRL-owned extensions and history.

## 6. Indivisible operating chain

```text
Mr.liou / MrLiouWord
  -> MRL root law and identity
  -> MRL_Mother registry, memory and runtime control
  -> MrliouAI unified operating identity
  -> MrlAPI / mrlclaude / mrlcloud internal extension layer

  -> local or external execution carrier
  -> external provider adapter when required
  -> execution result

  -> MRL_Mother backfill
  -> MRL historical lineage
```

The chain must remain complete. A provider adapter without MRL return is incomplete. A product without MRL upstream identity is incomplete. A result without trace and backfill is incomplete. An external source renamed as if it were MRL-owned is incorrect. An MRL-owned extension omitted in favor of a provider name is also incorrect.

## 7. Non-destructive extension rules

1. External original names, APIs, SDK identifiers, provider endpoints, documentation references and vendor-owned resources remain unchanged where required for interoperability.
2. MRL-owned implementations, wrappers, adapters, routing layers, histories and product modules use the MRL extension names defined here.
3. FlowAgent is not an external alias and must not be replaced by MrliouAI.
4. Historical MRL names and files are preserved. New names extend from their historical source instead of deleting or flattening it.
5. No MRL-owned module, capability, history or name may be removed merely to keep an external provider name intact.
6. No external provider asset is claimed as MRL-owned; only MRL-created extension, integration, orchestration, memory, runtime and product layers are named under MRL.
7. External source and MRL extension must coexist in the same provenance record.
8. Every execution must have an upstream authority reference and a downstream return path.
9. A layer may call another layer, but may not redefine its parent or erase sibling modules.
10. Historical reconstruction must add missing MRL links without deleting original evidence.
